## Layout

- `[app]/__init__.py` — `create_app(config=None)`: loads config, inits extensions, registers blueprints and error handlers
- `[app]/extensions.py` — extension objects (`db`, `migrate`, `login_manager`) created unbound, then `init_app()` in the factory
- `[app]/<feature>/` — one blueprint per feature: `routes.py`, `models.py`, `schemas.py` / `forms.py`, `services.py`, `templates/`
- `[app]/config.py` — config classes; secrets come from environment variables only
- `migrations/` — Flask-Migrate (Alembic) versions; generated, but reviewed
- `tests/` — `conftest.py` builds the app with a test config and yields `client` / `app`
- Do not edit `instance/` secrets, `.venv/`, or compiled static bundles

## Conventions

1. **App factory, no globals.** Never create the app at import time or import `app` from another module. Use `current_app` inside requests and `create_app()` in tests and CLI.
2. **Blueprints per feature.** New routes go in the matching blueprint; register blueprints only in the factory. Don't add a new top-level module pattern the repo doesn't use.
3. **Thin views.** Views parse input, call a service, and return one response. Business rules live in `services.py` so they can be tested without a request.
4. **Validate input.** `request.form`, `request.args`, `request.get_json()` and URL params are untrusted. Validate with [marshmallow / pydantic / WTForms] and return `400` (or re-render the form) with field errors. Use `get_json(silent=True)` and handle `None`.
5. **Database sessions.** Use the repo's `db.session`; commit once per request in the service or view, roll back on error. Use `db.get_or_404()` / `first_or_404()` instead of hand-rolled lookups. Watch for N+1 queries in loops and templates; use `selectinload` / `joinedload`.
6. **Migrations for every model change.** Generate with Flask-Migrate, read the autogenerated diff (Alembic misses renames and some type changes), and never edit an already-applied migration.
7. **Errors.** Register error handlers in the factory for `400`, `404`, `500` and the repo's custom exceptions, returning a consistent JSON shape for API routes. Never return stack traces; `debug=True` never in production.
8. **Security basics.** CSRF protection on form posts ([Flask-WTF]), `SECRET_KEY` from the environment, secure/HTTPOnly session cookies, Jinja autoescaping left on (no `|safe` on user input), no `render_template_string` with user data, parameterized queries only, and `send_from_directory` (never raw paths) for files.
9. **Authorization, not just login.** `@login_required` is not enough: check the current user may touch this record.
10. **Config.** Read secrets from environment variables in `config.py` only; document names in `.env.example`. Never read, print, or commit `.env*` or `instance/` secrets.
11. **Logging.** Use `current_app.logger` or the repo's logger. No `print()` left in views; never log passwords, tokens, cookies, or full request bodies.
12. **Dependencies.** Ask before adding a package or Flask extension. Prefer what's already in `pyproject.toml`.

## Testing

- pytest with the factory: a `conftest.py` fixture builds the app with `TESTING=True` and a test database, and yields `app.test_client()`.
- Test status codes, validation errors, auth and permission checks for new routes; unit-test services with external APIs faked at the boundary.
- New behavior gets a test; a bug fix gets a test that fails before the fix.

## Review habits (before you say "done")

- [ ] Diff is scoped to the ask — no drive-by refactors or reformatting of untouched files
- [ ] New routes validate input, check authorization, and return the right status codes
- [ ] Model changes have a reviewed migration; no N+1 queries added to list views or templates
- [ ] No secrets, stack traces, or PII in responses, templates, or logs; CSRF still on for forms
- [ ] No `|safe` / `Markup()` / `render_template_string` on user-controlled data
- [ ] Lint and relevant tests pass; `flask db upgrade` runs clean on a fresh database
- [ ] If you opened a PR: blockers-first summary (what breaks if wrong → what changed → how to verify)

## Boundaries — ask first

- Adding a dependency or extension, changing auth, session/cookie settings, CSRF, CORS, CI, or the database schema in a destructive way
- Upgrading Flask, Werkzeug, or SQLAlchemy major versions
- Deleting endpoints other clients may call, rewriting git history, force-pushing, or touching production infra or deploy config

## Never

- Create the app at import time, run with `debug=True` in production, or hard-code `SECRET_KEY`
- Concatenate user input into SQL, shell commands, file paths, templates, or redirects
- Edit an applied migration or disable lint/type rules project-wide to "make it green"
- Log tokens, cookies, or PII, or claim a task is done when tests or migrations failed
