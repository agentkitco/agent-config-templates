## Conventions

1. **Follow the existing structure.** Match current modules, naming and patterns. Don't add a second architecture (TCA, VIPER, etc.), DI container or networking library.
2. **Views stay small and declarative.** Split large `body`s into subviews; no networking, disk or heavy work inside `body` or `init`.
3. **One owner per state.** Use `@State` for view-local values, `@Binding` to pass write access down, and `@Observable` (or `@StateObject`/`@ObservedObject` on older code) for model objects. Don't create a view model inside `body`; own it once and pass it in.
4. **Concurrency, not callbacks.** Use `async`/`await` and `.task {}` (cancelled automatically when the view disappears). UI state updates happen on `@MainActor`. Don't silence data-race or `Sendable` warnings with `@unchecked Sendable` or `nonisolated(unsafe)` without a reason in the PR.
5. **No force unwraps or force tries** (`!`, `try!`, `as!`) outside tests and truly impossible cases. Handle errors and show loading, empty, error and offline states.
6. **Data behind protocols.** Views talk to view models, view models to services or repositories; inject them so tests can pass fakes. No `URLSession` calls from views.
7. **Previews.** Add a `#Preview` for new screens and components using sample data, not live services.
8. **Navigation.** Use the repo's pattern (`NavigationStack` with typed paths, coordinators, etc.); don't mix in a second one.
9. **Lists.** `ForEach`/`List` items need stable `Identifiable` IDs, not array indices, for dynamic data.
10. **Strings and styling.** User-facing text goes in the string catalog (`Localizable.xcstrings`) or `String(localized:)`; colors and fonts come from the asset catalog or design system, and use Dynamic Type text styles rather than fixed point sizes.
11. **Memory.** Watch for retain cycles in closures stored on objects (`[weak self]` where needed) and cancel long-running `Task`s you start manually.
12. **Secrets and storage.** Anything in the app bundle or `Info.plist` can be extracted, so treat it as public. Keep real secrets on a server; store tokens in the Keychain, not `UserDefaults`. Never commit signing certificates, provisioning profiles or `.p8` keys.
13. **Accessible by default.** Give icon-only buttons an `accessibilityLabel`, keep tap targets around 44pt, and check with the largest Dynamic Type size and VoiceOver.

## Testing

- Unit-test view models and services with fakes; mark tests `@MainActor` when they touch main-actor state, and `await` async code rather than using sleeps or expectations with long timeouts.
- UI tests find elements by `accessibilityIdentifier` and assert visible state; keep them few and focused on main flows.
- New behavior gets a test; a bug fix gets a test that fails before the fix where practical. Snapshot tests only if the repo already uses them.

## Review habits (before you say "done")

- [ ] Diff is scoped to the ask — no drive-by refactors, reformatting or unrelated `.pbxproj` churn
- [ ] Builds with no new warnings; unit tests and linter pass; UI tests run or noted as not run
- [ ] Checked on [simulator model / iOS version] and said which in the PR
- [ ] No new force unwraps, `try!`, or suppressed concurrency warnings; no secrets, certificates or profiles committed
- [ ] Async work tied to view lifetime (`.task`) or cancelled; UI updates on the main actor
- [ ] Loading, empty, error and offline states handled; list items have stable IDs
- [ ] New UI uses localized strings and theme colors, has accessibility labels, and works at large Dynamic Type sizes
- [ ] If you opened a PR: blockers-first summary (what breaks if wrong → what changed → how to verify)

## Boundaries — ask first

- Adding, removing or upgrading Swift packages, or changing the Swift version, Xcode version or deployment target
- Changing `Info.plist` keys, privacy usage strings, the privacy manifest (`PrivacyInfo.xcprivacy`), entitlements, capabilities, URL schemes or associated domains
- Changing signing, bundle ID, build settings or schemes, or SwiftData/Core Data model versions and migrations
- Archiving, uploading to App Store Connect or TestFlight, or running release Fastlane lanes
